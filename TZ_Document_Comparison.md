Постановка задачи

1.1. Цель

Создать программный комплекс, который автоматически сравнивает две версии офисных документов (форматы DOC, DOCX, PDF, включая сканированные файлы) и выявляет смысловые изменения, то есть правки, которые реально влияют на содержание документа (например, изменение сроков, сумм, обязанностей или условий договора).
Решение должно игнорировать косметические изменения, такие как пунктуация, форматирование или перефразирование без изменения смысла.

1.2. Основная идея

Система должна выполнять глубокое сравнение документов не только по тексту, но и по их семантике, используя методы NLP и большие языковые модели (LLM).
Результатом является отчёт о различиях, в котором указаны:
	•	изменённые фрагменты;
	•	категория изменений (сроки, обязательства, финансовые параметры и т.д.);
	•	оценка влияния изменений (низкое / среднее / высокое);
	•	краткое описание сути изменений.

2. Основной Pipeline обработки документов

Пайплайн включает 6 ключевых этапов, объединяющих классический diff-анализ и LLM-интерпретацию.

Этап 1. Приём и идентификация документов

Вход: две версии одного документа (Base и Target).
Задачи:
	•	загрузка файлов через API или UI;
	•	определение формата (DOC, DOCX, PDF);
	•	генерация уникального case_id (кейса сравнения);
	•	сохранение оригиналов в файловом хранилище (S3 или аналог).

⸻

Этап 2. Извлечение и нормализация текста

Инструменты:
	•	DOC/DOCX → python-docx;
	•	PDF (текстовый) → PyMuPDF или pdfminer.six;
	•	PDF (скан) → OCR (tesseract или Azure Document Intelligence).

Шаги:
	•	извлечение текста и структуры (разделы, абзацы, нумерация);
	•	очистка колонтитулов, номеров страниц, мусора;
	•	унификация пробелов, пунктуации, числовых форматов;
	•	сегментация на смысловые блоки (раздел/параграф/предложение);
	•	сохранение нормализованного текста в JSON-структуру.

⸻

Этап 3. Сопоставление и технический diff

Цель: найти участки, в которых тексты различаются.

Инструменты:
	•	difflib / chopdiff / rapidfuzz / git + pandoc.

Действия:
	•	выравнивание текстов по абзацам или предложениям;
	•	вычисление различий (added, removed, modified);
	•	фильтрация «шума» (изменения регистра, пробелов, пунктуации);
	•	формирование структуры изменений (ChangeItem): Этап 4. Семантический анализ изменений (LLM Layer)

Цель: определить, изменился ли смысл текста, и классифицировать изменения.

Инструменты:
	•	LLM API;
	•	эмбеддинги  — для оценки близости смыслов.

Действия:
	•	для каждого изменения модель определяет:
	•	semantic_change — влияет ли на смысл (да/нет);
	•	category — тематическая группа (сроки, обязательства и пр.);
	•	impact — степень влияния (низкое / среднее / высокое);
	•	summary — краткое пояснение (RU).
	•	объединение результатов в сводку (overview);
	•	сохранение классифицированных данных в БД.

⸻

Этап 5. Формирование отчёта

Цель: предоставить пользователю понятный результат.

Форматы:
	•	HTML — интерактивный отчёт с подсветкой diff;
	•	PDF — финальный документ с таблицей изменений и сводкой;
	•	JSON — структурированные данные для интеграций;
	•	PATCH — унифицированный diff для систем контроля версий.

Содержание отчёта:
	•	общее количество изменений;
	•	классификация по категориям;
	•	краткое описание сути каждого изменения;
	•	агрегированная оценка (что изменилось по смыслу).

⸻

Этап 6. Хранение, доступ и мониторинг

Компоненты:
	•	База данных PostgreSQL — хранение текстовых версий, diff, отчётов;
	•	S3-совместимое хранилище — оригиналы и артефакты;
	•	Redis — кэш и очередь задач;
	•	Мониторинг: Prometheus + Grafana, Sentry.

Функции:
	•	история сравнений;
	•	доступ по API/UI;
	•	логирование времени обработки, ошибок и метрик качества.

⸻

3. Основные функциональные возможности
	•	Поддержка форматов DOC/DOCX/PDF (в т.ч. OCR для сканов);
	•	Сегментация и diff на уровне предложений;
	•	Семантическая фильтрация и классификация изменений;
	•	Вывод отчётов в HTML, PDF, JSON;
	•	API-интерфейс для интеграций;
	•	Поддержка русского языка и кастомных справочников категорий;
	•	Возможность адаптации промптов под домен (юридический, финансовый и т.п.). Пример пользовательского сценария
	1.	Пользователь загружает старую и новую версию договора.
	2.	Система извлекает текст и нормализует его.
	3.	Выполняется diff-анализ → список изменений.
	4.	LLM оценивает, какие изменения влияют на смысл.
	5.	Формируется отчёт, где отражено:
	•	что изменилось,
	•	к какой категории относится правка,
	•	насколько она значима.
	6.	Пользователь получает HTML/PDF отчёт и JSON-результаты.
